# 安全策略数据流与同步机制设计方案

本方案重点阐述前后端如何配合实现“域名拦截规则条数”、“用户封禁 IP 数量”以及“拦截请求总次数”的数据获取，以及配置变更时的实时同步机制。特别针对**拦截次数统计的持久化和准确性**进行了深入设计。

## 需求拆解与数据来源分析

我们需要在首页展示并同步三项数据：
1. **域名拦截规则条数**：来源于后端配置文件中的 `AccessRules` 数组。
2. **用户封禁 IP 数量**：来源于后端配置文件中的 `UserBlockRules` 数组。
3. **总拦截次数 (对应UI“今日拦截”)**：这是一个**自代理启动以来的累加统计指标**，不能依赖前端的动态日志池长度。

---

## 核心挑战：为什么不能用 `interceptLogs.length`？
如果单纯依赖前端 `interceptLogs.length` 会导致以下严重问题：
1. **最大限制丢失**：前端内存日志通常有上限（例如 `MAX_INTERCEPT_LOGS = 500`），超过后旧日志会被挤出，导致总数永远卡在 500。
2. **清空操作误伤**：用户在界面点击“清空日志”时，前端数组被清空，会导致主界面的拦截统计瞬间归零。
3. **离线丢失**：如果用户关闭了前端控制台，后端继续代理拦截产生的记录，前端再次打开时会丢失这部分统计。

## 前后端架构设计思路 (后端权威 + 前端解耦方案)

### 1. 后端设计 (Backend - Go 绝对权威)
为了保证统计的绝对准确，“总拦截次数”必须由**后端**进行统计和维护。该计数的生命周期与后端代理服务器进程的生命周期一致（即服务器重启后归零）。

- **静态规则存储**：
  - 后端通过 `config.json` 持久化保存 `AccessRules` 和 `UserBlockRules`。
- **动态状态（总拦截计数器）**：
  - 后端内存中维护一个线程安全的计数器字段 `InterceptCount` (例如使用 `atomic.Uint64` 或通过互斥锁保护)。
  - **触发更新**：代理核心每次发生拦截时，该计数器直接原子自增 +1。
- **数据暴露方式**：
  - **接口侧 (API)**：后端提供类似 `GET /api/stats`（或合并在 `GET /config` 返回体中）的接口，供前端首次打开时拉取当前的 `InterceptCount` 绝对值。
  - **推送侧 (WebSocket)**：在推送实时拦截日志（`intercept_logs`）时，在消息的 payload 中附加当前的绝对拦截总数。前端每次收到推送，直接覆盖本地计数即可，防止网络重连导致少算或重复计算。

### 2. 前端设计 (Frontend - Vue 3 + Pinia 解耦)
前端需要将**“拦截日志列表视图”**与**“拦截总次数统计视图”**彻底解耦。

- **统一状态管理 (Store)**：
  - 在 `src/stores/websocket.js` 中维护 `config`（规则数组）、`interceptLogs`（仅用于UI表格展示的日志流水，允许被随时清空）以及一个**全新的独立字段** `InterceptCount`（数值类型，用于主界面总览展示）。
- **同步机制 (Reactive Data Flow)**：
  - **初次加载**：
    1. 首页挂载时检查规则，若无则调用 `store.loadConfig()`。
    2. 首页挂载时通过接口返回或等待 WS 初始推送获取 `InterceptCount` 的初始值。
  - **配置变更同步**：
    当在 `AccessControl.vue` 中修改规则保存时，调用 `store.saveConfig()`，同步更新本地的 `store.config`，首页因 Vue 响应式机制立刻无刷新更新“规则条数”和“IP数量”。
  - **拦截次数实时同步**：
    当 WebSocket 收到新的拦截推送时：
    1. 将明细日志追加到 `interceptLogs` 供表格展示。
    2. **更新 `InterceptCount`**：从 WebSocket payload 中读取后端传来的最新绝对值，覆写 `InterceptCount`。
  - **用户清空操作**：
    当用户点击“清空日志”时，仅执行 `interceptLogs = []` 清理视图，**绝不修改** `InterceptCount`。这样既满足了用户清理界面的需求，又保证了全局宏观统计数据的真实性和连续性。

## 总结数据链路

1. **规则统计链路 (双向同步)**：
   `前端修改` -> `API 保存` -> `后端落盘 & 内存更新` -> `前端 Store 更新` -> `首页实时刷新条数`。
2. **总拦截统计链路 (单向数据流，后端权威)**：
   `前端首次加载获取绝对值` -> `后端拦截事件发生，计数器自增` -> `后端 WebSocket 携带最新总数下发` -> `前端 Store.InterceptCount 更新` -> `首页实时跳动更新` -> `无论前端如何清空日志，统计数字永远单调递增，直至代理服务器重启
